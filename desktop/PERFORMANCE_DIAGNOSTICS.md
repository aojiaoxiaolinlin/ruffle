# 桌面端卡顿诊断

默认构建保留原有的五秒汇总。需要定位帧间隔和具体阶段时，显式启用：

```powershell
cargo build -p ruffle_desktop --release --features performance_diagnostics --locked
```

此功能同时启用渲染器的详细统计。使用 Release 测试，保持窗口大小、画质、滤镜比例与复现问题时一致。可通过 `--cache-directory` 指定独立日志目录，通过 `--config` 复用原配置和登录票据。

日志过滤器应包含 `ruffle_desktop=info,ruffle_core::performance_diagnostics=info,ruffle_render_wgpu=info`。

每五秒输出有界汇总：

- `Perf progress`：运行帧尝试次数、一次 tick 中的补帧次数、清空积压帧次数、音频同步调整及游戏忙等带来的时间偏移。
- `Perf phase`：阶段次数、平均值、毫秒直方图的 p95 上界、最大值及超过 42/83 毫秒的次数。直方图尾部使用实际最大值作为上界。
- `Perf stall`：超过约 83 毫秒的阶段或间隔，附日志时间戳；每五秒最多 12 条，防止日志刷屏影响测试。完整次数仍在汇总中。

`core.frame-gap` 是通过预加载检查后的逻辑帧起点间隔；`desktop.redraw-gap` 是窗口重绘起点间隔。它们与 `render_hz` 的平均吞吐不同。窗口隐藏、暂停、切图和加载过程应单独判断。

核心阶段覆盖预加载、帧脚本、GC、Socket、网络连接、定时器和媒体流；桌面阶段覆盖输入、异步任务、事件批次间隔、唤醒延迟、GUI、获取表面、提交和呈现。时间均为 CPU 墙钟时间，嵌套阶段有重叠，不能相加，也不表示 GPU 执行耗时。`frame_steps` 计数包含可能因预加载而提前返回的运行帧尝试。

桌面循环还记录 `about-to-wait` 总耗时、手柄轮询、下一帧调度和重绘检查。`wait-requested` 是 winit 提供的请求等待时长，`wait-elapsed` 是实际等待区间；`wake-lateness` 与 `interrupted-wake-lateness` 分别观察定时唤醒与事件打断时超过原定截止时间的部分。等待区间可能包含系统消息处理，不能直接解释成操作系统没有调度线程。

阶段日志仅记录固定标签和数值，不记录输入事件内容、账号、票据或脚本值。其它已有日志仍可能包含游戏数据，不应直接公开整个日志目录。

复现时记录进入游戏、移动、战斗以及明显卡顿的大致时间。关闭程序会补写最后一段统计。先对照间隔异常和对应阶段，再决定是否需要画质对照或 GPU 专项分析；不能单凭平均帧率或某次启动峰值确定原因。

## 洛克鼠标输入与帧循环

Windows 线程采样确认过一种累计耗时：多个鼠标事件连续触发 `update_mouse_state`、游戏 `gotoAndStop` 和嵌套帧脚本，单次处理不慢，但消息队列持续繁忙，推迟 `about_to_wait` 中的 tick。判断时需要对照一整段调用栈，不能只比较单次阶段最大值。

曾尝试按电影帧率合并连续鼠标移动，实机出现点击失效，因此已撤回，恢复原有输入路径。缓冲器单元测试不能替代游戏内的命中与点击验证。后续应优先处理事件队列繁忙时帧更新得不到执行的调度问题，并保持原有输入顺序。

### Windows 通用帧调度

Windows 桌面端对所有电影启用输入繁忙时的帧调度，不依赖游戏身份或登录功能。只在窗口可见且已加载时生效：每个原始移动、按键或鼠标按钮事件完整处理之后检查期限；到期则用同一播放器时钟推进 tick，并在需要时直接呈现画面，避免 Windows 低优先级的 `WM_PAINT` 继续被输入队列推迟。常规事件、鼠标坐标和按钮按下/抬起路径不作缓冲或合并。长时间落后时不循环补调度，实际补帧仍由 Player::tick 管理。其它平台的调度不变。

普通 Release 构建即包含修复，详细日志仍需显式启用：

```powershell
cargo build -p ruffle_desktop --release --locked --offline
cargo build -p ruffle_desktop --release --locked --offline --features performance_diagnostics
```

验证游戏内按钮、点击移动、按住拖动、右键菜单和文字输入，再对比移动与战斗时的 `core.frame-gap`、`desktop.redraw-gap` 和补帧/丢弃积压帧次数。`desktop.fair-frame-service` 记录调度介入；`desktop.mouse-down/up-received`、`desktop.mouse-down/up-game`、`desktop.mouse-button-ui-consumed` 区分按钮到达、游戏派发和 GUI 消费，仅记录计数和耗时。

2026-10-24 实机反馈不卡顿。对应采集 `fair-frames-20261024-155318-710` 中，排除启动后的 13 个有调度活动的五秒窗口共记录 1563 个逻辑帧间隔，最大 95.212 ms，超过 83 ms 共 2 次；对应重绘间隔最大 96.782 ms。全次记录有 95 次鼠标按下和 95 次抬起送入游戏，另外 4 个按钮事件由 GUI 消费。此前反复出现的半秒停顿在这组正常游玩窗口中未再出现；启动加载峰值应单独分析。单元测试只验证调度策略，不能替代游戏内的输入与画面验证。

### 共用调度候选的对照方法（历史记录）

上面的早期实机结果仅验证了洛克；此前卡布流畅时仍走原有调度，不能证明共用调度对卡布兼容。推广前曾使用临时 `shared_frame_scheduling` 功能生成跨游戏候选构建，与仅对洛克启用调度的构建对照。验证结果见下节。现在已移除该临时功能，普通 Windows 构建默认使用共用策略，详细诊断仍是可选功能。

对照时由同一份源码生成 `ruffle-frame-scheduling-baseline.exe` 和 `ruffle-frame-scheduling-shared.exe` 两个 Release 程序。这些文件名描述当时的构建，当前源码不再提供该临时 A/B 开关。

基线程序保留洛克专项调度，卡布走原路径。候选程序让两款游戏及其它 SWF 进入同一个调度路径。两者使用同样的画质、舞台对齐、输入逻辑和详细日志。

对照构建的 `Frame scheduling context` 记录固定游戏类别及调度范围；`.roco`、`.kabu`、`.other` 的介入计数证明对应游戏实际执行过新调度。推广后的基础实现只保留调度范围及通用 `desktop.fair-frame-service` 标签，去除对游戏类别的依赖。均不记录账号或票据。

对照要求尽量保持窗口大小、同一地图和操作相近；进入游戏后持续移动鼠标，检查按钮、点击移动、按住拖动、右键菜单和输入文字，并播放战斗动画。每段正常游玩 30–60 秒，启动加载单独分析。比较逻辑帧间隔、重绘间隔、补帧/丢弃积压次数及按钮派发情况，并结合实机反馈决定是否推广到默认调度。

### 2026-10-24 共用调度实机对照结果

用户完成 baseline/shared 各两款游戏共四次测试，反馈均流畅，未感觉出差别。采集目录为 `shared-frame-baseline-20261024-201316-426` 与 `shared-frame-shared-20261024-201554-404`。分析只提取固定调度标签和性能计数，不复制游戏日志或登录数据。

结论：通过洛克与卡布的共用调度实机回归，将策略推广为 Windows 桌面默认调度。卡布原本流畅，这次主要提供启用后的兼容性证据；不同操作、时长及加载状态使这组测试不能证明提升幅度，也不代表所有 Flash 内容均已验证。Android 调度未改变。基础优化已去除依赖游戏身份的启用条件；登录、票据保存、洛克舞台对齐属于单独的功能提交。
