## 源码解释

实际依赖是registry gc-arena 0.7.0。Metrics::allocation_debt按新Gc分配数量减去已做工作的credits计算。Arena::collect_debt只做到debt为0，没有每次调用的最小工作量；频繁调用不代表每次都推进。

默认sleep_factor=0.5；标记/trace/保留的工作系数为0.1/0.4/0.05。分配数量较少而存活图较大时，唤醒与完成当前周期可能在墙钟上被摊到数分钟。这与实机阶段记录一致，但还不能排除长期对象保留，也不能解释全部CPU/GPU/驱动或分配器内存。

## 默认关闭的诊断实验

仅performance_diagnostics构建识别RUFFLE_DIAGNOSTIC_GC_WORK_FLOOR=1，未设置/0/无效值均关闭。普通构建不包含策略字段和逻辑。没有改默认Pacing、sleep_factor或强制完成整轮GC。

开启时，仅在已经活动的GC阶段，每50ms最多一次将待执行工作补至2000对象计数单位；原分配已提供足够工作时不追加，并仍消耗本次时隙，避免高频输入循环在后续低debt调用中重复补量。它限制补量频率，不保证单次trace/drop的硬时间上限。不会保留任何对象引用或改变可达性。

两个新增回归已通过：一万个同时间戳更新也只能补一次，休眠时不唤醒、额度足够时不重复补量；在停止分配且普通collect_debt不再前进的实际Arena中，策略可通过增量调用完成周期，全部存活节点保持。

完整核心诊断测试169 passed、0 failed、1个既有手工实验ignored；普通桌面cargo check、诊断release构建及格式/diff检查通过。加入60万个存活节点的逐节点完整性断言后，模型再次通过且峰值/逻辑阶段时长一致；工作下限组最大单次耗时此次为1.802ms，说明墙钟耗时确有运行间波动，不能给出硬暂停保证。
